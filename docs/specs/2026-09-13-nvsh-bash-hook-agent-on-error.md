# nvsh bash hook + agent on error

> nvsh elevates your existing bash into a self-healing NVIDIA shell: install one sourced hook, keep bash exactly as it is, and when a command fails an NVIDIA-opinionated agent (Pi.dev driving the local associate model by default) appears inline with a diagnosis and a proposed fix you approve, retry and verify; /ask, /fix, /doctor and Ctrl+G reach the same agent on demand, and successful commands never pay a millisecond for it.
> instruction: Verify end to end on the Spark in Ghostty and on orin over ssh, orin both with and without tmux: 'nvsh setup', a successful command shows nothing new, 'ls /nope' shows the panel with the real error slice, /doctor and Ctrl+G reach the agent, 'nvsh uninstall' restores the shell.

## Audience

- Operators (starting with Ori) who live at a bash prompt on NVIDIA Jetson AGX Orin/Thor and DGX Spark machines, locally in Ghostty and over ssh, and who want an NVIDIA engineer to appear only when something breaks.
  - instruction: Check README's first paragraph names Jetson, DGX Spark, bash and ssh as the setting; run the hook on spark, thor and orin.

## Before → After

- Before: Today a failure on a Jetson or Spark means copying the error into a chat, re-deriving the machine's JetPack/CUDA/unified-memory facts by hand, and typing fixes back; nvsh itself is a scaffold with no shell behaviour (README.md:10-14) and its prompts still describe a PTY wrapper.
- After: After 'nvsh setup', the operator's own bash is unchanged on success; a qualifying failure shows an inline ⚡ nvsh panel within a second with a diagnosis built from the real output slice and the machine's detected facts, offers a proposed fix that runs only after Enter, retries, and reports whether it worked; /ask, /fix, /doctor, /explain, /retry and Ctrl+G reach the same warm pi session; 'nvsh uninstall' removes everything.
  - instruction: Demonstrate on the Spark in Ghostty with a CUDA-OOM-style failure and on orin over ssh with a missing-package failure; record both as GIFs or screenshots in docs/.

## Why it matters

- The value is NVIDIA-specific and local: unified memory on GB10/Jetson, L4T/JetPack version skew, container runtime and power mode are what a generic 'explain my error' tool gets wrong, and the machines are often air-gapped, so the agent must run against a local model with the facts collected on-box.

## Requirements

- Zero cost on the success path: the sourced bash hook is a pure-bash function that reads $? and PIPESTATUS, applies the cheap trigger pre-filter (0, 130, 141, empty line, leading-space/ignored history) in bash, and only execs the Python entrypoint when a failure qualifies. Measured on this Spark: the uv-tool entrypoint costs ~45 ms (associate --help 0.051 s, nvsh --help 0.043 s), which is too much to pay on every prompt but fine on a failure.
  - honesty: Sourcing the hook and running 1000 successful commands in 'bash --norc -i' forks no nvsh process (strace -f -e execve count of nvsh == 0) and adds < 5 ms median to prompt latency.
- Trigger rules are a table-tested pure-Python module (nvsh/triggers.py) consulted by the entrypoint before any agent call: 130, 141, grep/diff exit 1, false, test/\[ \], commands run inside scripts, pipelines without pipefail (PIPESTATUS is passed in by the hook), interactive/long-running programs, plus a rate limit. Pattern triggers for exit-0 failures are opt-in.
  - honesty: tests/`test_triggers.py` is table-driven over (command, exit, PIPESTATUS, interactive-program flag, rate state) and covers every rule in CLAUDE.md's trigger list; all non-error rows produce 'no call'.
- Slash commands (/ask /fix /explain /retry /doctor /context /agent /help) are routed inside the same bash session by binding Enter (C-m) to a readline macro that first runs a bind -x function then accept-line (C-j). The function inspects `READLINE_LINE`: a line whose first word is a registered slash command is rewritten to a hidden `nvsh slash <line>` call prefixed with one space (so HISTCONTROL ignorespace keeps it out of history) and the original line is pushed with 'history -s'. Unregistered '/foo', absolute paths, quoted multi-line input and plain commands pass through unchanged. Verified in a throwaway bash 5.2 under script(1) on the Spark: /doctor and '/ask why is memory high?' routed, /notacmd and 'ls -d /tmp' ran as bash, a quoted two-line echo (Enter inside the quotes) continued normally. `command_not_found_handle` does NOT fire for '/doctor', so this rebind is required.
  - honesty: In an interactive Ghostty session on the Spark with Ghostty's own integration loaded: /doctor routes, 'history' shows '/doctor' and not the dispatch line, '/tmp/x' runs as a path, a quoted two-line echo (Enter pressed inside the quotes) continues, and no visible flicker or duplicated prompt appears.
- Completion: 'complete -I -F' (bash >= 5 initial-word completion) supplies the '/'+Tab palette: for a first word starting with '/' and containing no second '/', it merges registered slash commands with compgen -f path matches, so '/'+Tab lists /ask /doctor ... next to /etc /tmp, '/do'+Tab completes to /doctor, '/tm'+Tab still completes /tmp/, and every other word falls through via compopt -o bashdefault -o default ('ec'+Tab still lists echo). `complete -F <fn> /doctor` supplies per-command argument completion ('/doctor '+Tab lists gpu docker cuda memory services). Verified on the Spark in a throwaway bash 5.2 with bash-completion 2.11 loaded. fzf and ble.sh stay optional.
  - honesty: '/'+Tab, '/do'+Tab, '/doctor '+Tab, '/tm'+Tab and 'ec'+Tab behave as in scope entry s18 in a real Ghostty session and over ssh to orin (no bash-completion assumptions beyond the stock package).
- Agent boundary: nvsh/agent/ defines a small NvshAgent contract (request kinds failure|slash|explicit, streamed events text-delta|tool-call|proposal|status|done|error, cancel, capabilities) with a FakeAgent for tests and PiAgent as the default. PiAgent spawns 'pi --mode rpc' (pi 0.84.2 installed, JSONL over stdio with prompt/abort/`get_state`/`switch_session` commands and `message_update`/`tool_execution_`\* events, documented in the shipped docs/rpc.md) as one long-lived subprocess per shell session so a failure does not pay pi's ~0.35 s node startup each time.
  - honesty: nvsh/agent/ imports nothing from pi; FakeAgent drives the full failure -> proposal -> approve -> retry -> verify loop in tests without pi installed; PiAgent's rpc reader splits on LF only and handles abort and a killed pi process without hanging the shell.
- Deterministic nvsh tools (`inspect_gpu`, `inspect_memory`, `inspect_containers`, `inspect_services`, `read_logs`, `retry_command`, verify) are implemented once in Python. To expose them to Pi as first-class tools, nvsh ships one generic TypeScript extension file loaded via `pi -e <path>` that forwards each call to `nvsh tool <name> --json`; pi has no RPC command to register tools from outside the process (verified in docs/extensions.md and docs/rpc.md). Mutating proposals surface as 'proposal' events and are confirmed by the operator in nvsh, mirroring shell-cli's operations.py apply=False default and deny-wins policy. (Per decision c25, v1 uses only pi's bash tool; the extension shim is the later migration path.)
  - honesty: No agent-proposed command ever runs without an explicit operator keypress; the audit log records every proposal, the decision and the outcome; the fixture test asserts a 'sudo rm -rf' proposal is shown but never executed.
- Default model: nvsh's config ($`XDG_CONFIG_HOME`/nvsh/config.toml: \[agent\] provider=pi, \[agents.pi\] provider=nemotron model=associate) names Pi's own provider/model; the endpoint (a lobes-gateway at 192.168.1.138:8000, NOT this machine, which is 192.168.1.157) and its bearer key stay in ~/.pi/agent/models.json. nvsh never stores or forwards keys, and 'nvsh doctor' reports whether pi is on PATH and whether the configured provider answers /v1/models (both endpoints answered '`invalid_api_key`' unauthenticated, so reachability is a 401-vs-timeout check).

## Scope / boundaries

- No third-party runtime dependencies (pyproject dependencies=\[\] stays); pi is an external optional binary, never a Python dependency, and absence of pi, tmux, fzf, spark (dgx-spark-cli) or any NVIDIA tool degrades a feature, never breaks the shell.
- Untouched: culture.yaml (backend stays claude, never rewritten by code), .claude/skills (vendored verbatim from guildmaster), the .pi/skills relative symlink and the no-.pi/settings.json rule enforced by tests/`test_pi_settings.py`, and doctor's `_PROMPT_FILE` table which tests/`test_harness_registries.py` pins to backend-fingerprints.yaml.
- No endpoint or key lands in tracked JSON: scripts/scan-secrets.py fails CI on any non-localhost http URL under baseUrl/endpoint/url/host keys in JSON files, so config examples use localhost placeholders and the real provider mapping lives only in ~/.pi/agent/models.json on the machine.

## Non-goals

- nvsh is not built as a login shell or PTY wrapper in this scope: no chsh, no /etc/shells entry, no 'install-shell', no argv\[0\]='-nvsh' handling. The operator keeps /bin/bash (verified as the login shell on spark, thor and orin). This retires the 'Login-shell constraints' section of CLAUDE.md:122-152; a wrapper can be revisited later behind the same NvshAgent and tools layer.
- nvsh does not re-implement or depend on jetson-cli, rtx-spark-cli or callsmith: all three are unrewritten culture-agent-template scaffolds with zero domain code (jetson-cli/CLAUDE.md:9-18; grep for `nv_tegra_release`/nvpmodel/guard returned nothing). Only dgx-spark-cli ('spark', spark/probe/\*.py) is real and is called when installed.
- Deferred past this scope: known-good state (/remember-good, /diff-good, /restore-good), the OpenAI first-class adapter (issue #6 MVP step 7), zsh/fish integrations, fzf/ble.sh palettes (level 2/3 of issue #5), and pattern triggers for tools that fail with exit 0.

## Assumptions

- Output capture without a PTY wrapper: the hook cannot see the failed command's output. v1 captures it by re-running on demand under 'script -qec' (util-linux 2.39.3 installed) for /retry and 'nvsh run', and by 'tmux capture-pane -p' when $TMUX is set (tmux 3.4 installed). 'exec > >(tee)' is rejected because it breaks isatty and colors.
- Snappy means: a successful command adds one bash function call (no fork) before the next prompt; a qualifying failure shows the first agent text within about a second on the Spark because the pi rpc process is already warm; Ctrl+G and /ask reuse the same warm session; and everything renders in a plain 80-column SSH terminal (thor and orin are reached only over ssh) with 256-colour output optional.

## Decisions

- Architecture: nvsh HOOKS into the operator's existing bash instead of wrapping it. 'nvsh install bash' appends one 'source ~/.local/share/nvsh/bash.sh' line to ~/.bashrc, the sourced file appends to the `PROMPT_COMMAND` array (bash>=5.1; this Spark runs 5.2.21, verified) without clobbering an existing `PROMPT_COMMAND`, and 'nvsh uninstall' removes it. This flips CLAUDE.md:111-120 and QWEN.md:43-45, which currently record a PTY-wrapper-as-login-shell decision.
- v1 agent tooling: pi gets the nvsh system prompt, the bounded failure context and its built-in bash tool; every mutation still surfaces as a proposal the operator approves in nvsh. nvsh-specific skills and resident deterministic tools are prototyped in the associate harness first and migrated into nvsh when proven.
- Output capture rule: diagnose first from exit status, command line, PIPESTATUS and machine context; ask before any re-run under script(1); use tmux capture-pane only when already inside tmux. No silent re-execution ever.
- 'nvsh setup' installs the capture layer along with pi and the hooks: a per-session typescript via util-linux script(1) (present on spark, thor, orin) started from the hook file when the shell is interactive, not already under script or tmux, and not nested; tmux is installed/used when the operator wants a multiplexer (orin lacks it; apt candidate 3.4) and then tmux pipe-pane is the log source instead. Either log is sliced per command by Ghostty's OSC 133 C/D markers, which nvsh's hook file re-sources from /usr/share/ghostty/shell-integration/bash/ghostty.bash when `TERM_PROGRAM`=ghostty (or emits itself elsewhere). So the failed command's actual output is available without any re-run; re-run stays ask-first.

## Hard questions

- risk: The Enter rebind (bind -x on C-m) is unverified interactively; if it cannot chain to accept-line cleanly the slash-command surface falls back to a 'nvsh ask ...' prefix or a Ctrl+G-only palette.
- risk: The Enter macro makes readline redraw the prompt line after the bind -x function on every command (harmless in the script log, but needs a real Ghostty check for flicker, multi-line PS1 and duplicated OSC 133 prompt markers).
- Shipping a TypeScript pi extension inside a Python package: acceptable for v1 so nvsh tools are first-class pi tools, or should v1 give pi only a prompt plus the 'bash' RPC tool and keep all tool execution on the nvsh side? (resolved: v1 gives pi only the prompt and its built-in bash tool (no TypeScript shim). nvsh skills and resident deterministic tools are explored first inside the associate harness (~/git/associate), then migrated into nvsh once they prove out.)
- Is re-running the failed command under script(1) acceptable as the default way to capture its output for diagnosis (it re-executes side effects), or should v1 only diagnose from exit code + command line unless the session is inside tmux? (resolved: nvsh never re-runs a failed command silently. It first diagnoses from exit code, command line, PIPESTATUS and machine context; if output is needed it asks the operator before re-running under script(1), because the command may have side effects. Ghostty gives OSC 133 prompt/command markers, not a programmatic read of the scrollback, so it does not replace this rule.)
- On the Jetsons pi is not installed. Should nvsh install pi (npm/nvm) as part of 'nvsh install', or point the Jetsons at the stdlib OpenAI-compatible adapter against the gateway on the Spark? (resolved: When pi is missing, nvsh offers to install it, or lets the operator pick another harness: Qwen Code, Claude Code, Codex. Each is one adapter behind NvshAgent.)
- CLAUDE.md says the operator goal (default login shell via chsh) overrides conflicting issue text, and the user now says hook, don't replace. Is the login-shell goal dropped, or parked as a later phase built on top of the hook? (resolved: Parked, not dropped: nvsh hooks into bash; a login-shell wrapper is a later phase, if ever. Supporting a wrapped bash is judged far harder than the hook.)
